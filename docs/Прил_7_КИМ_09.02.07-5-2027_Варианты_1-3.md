# ПРИЛОЖЕНИЕ 4

## Задание: Валидация форм и обработка ошибок в Python-приложении

## Продолжительность выполнения

30 минут (0 ч. 30 мин.)

## Максимальный балл

25 баллов

## Текст задания

Разработать API с формой регистрации пользователя, реализующее валидацию ввода и обработку ошибок.

## Требования к базе данных

Создать таблицу registrations в базе данных PostgreSQL со следующей структурой:

| **Имя поля** | **Тип данных** | **Описание** |
| --- | --- | --- |
| id | SERIAL PRIMARY KEY | Идентификатор |
| username | VARCHAR(50) UNIQUE NOT NULL | Логин |
| email | VARCHAR(100) UNIQUE NOT NULL | Email |

Заполнить таблицу не менее чем 3 тестовыми записями.

## Требования к API

- POST /api/registrations — регистрация пользователя
- Принимает JSON с полями: username, email
- Возвращает HTTP 201 при успешной регистрации
- Возвращает HTTP 400 с описанием ошибок валидации:
    - поле username: обязательное, от 3 до 20 символов
    - поле email: обязательное, содержит символ «@»
- HTTP 409 — пользователь с таким логином или email уже существует
- HTTP 500 — ошибка сервера

## Требования к тестированию

Составить пакет тест-кейсов (не менее 6 тест-кейсов) для проверки API валидации.

Каждый тест-кейс должен содержать:

- ID тест-кейса
- Название
- Предусловия
- Шаги тестирования (пошагово)
- Ожидаемый результат
- Фактический результат (оставить пустым для заполнения экспертом)
- Приоритет (high / medium / low)

Обязательные тест-кейсы:

1. Успешная регистрация с корректными данными (HTTP 201)
2. Регистрация с пустым логином (HTTP 400)
3. Регистрация с логином короче 3 символов (HTTP 400)
4. Регистрация с email без символа «@» (HTTP 400)
5. Регистрация с уже существующим логином (HTTP 409)
6. Регистрация с уже существующим email (HTTP 409)

# ПРИЛОЖЕНИЕ 4

## Задание: Логирование действий пользователя

## Продолжительность выполнения

30 минут (0 ч. 30 мин.)

## Максимальный балл

25 баллов

## Текст задания

Реализовать систему логирования действий пользователей в информационной системе с использованием Python и PostgreSQL.

## Требования к базе данных

Создать таблицу audit_log в базе данных PostgreSQL со следующей структурой:

| **Имя поля** | **Тип данных** | **Описание** |
| --- | --- | --- |
| id | SERIAL PRIMARY KEY | Идентификатор записи |
| user_id | INTEGER NOT NULL | Идентификатор пользователя |
| username | VARCHAR(50) NOT NULL | Логин пользователя |
| action | VARCHAR(50) NOT NULL | Действие (CREATE, UPDATE, DELETE, LOGIN, LOGOUT) |
| table_name | VARCHAR(50) NOT NULL | Имя таблицы |
| record_id | INTEGER | Идентификатор записи |
| timestamp | TIMESTAMP DEFAULT NOW() | Время действия |

Заполнить таблицу не менее чем 5 тестовыми записями.

## Требования к API

- POST /api/actions — записать действие пользователя в журнал (принимает JSON: user_id, action, table_name, record_id)
- GET /api/logs — получить журнал действий (JSON-массив, HTTP 200)
- GET /api/logs?user_id=N — фильтрация журнала по пользователю
- HTTP 400 при некорректных данных, HTTP 500 при ошибке сервера

## Требования к тестированию

Составить пакет тест-кейсов (не менее 6 тест-кейсов) для проверки API журналирования.

Каждый тест-кейс должен содержать:

- ID тест-кейса
- Название
- Предусловия
- Шаги тестирования (пошагово)
- Ожидаемый результат
- Фактический результат (оставить пустым для заполнения экспертом)
- Приоритет (high / medium / low)

Обязательные тест-кейсы:

1. Запись действия CREATE в журнал (POST, HTTP 201)
2. Запись действия LOGIN в журнал (POST, HTTP 201)
3. Запись действия с несуществующим пользователем (HTTP 400)
4. Получение полного журнала действий (GET, HTTP 200)
5. Фильтрация журнала по пользователю
6. Ошибка сервера при недоступной БД (HTTP 500)

# ПРИЛОЖЕНИЕ 4

## Задание: Генерация отчётов с визуализацией данных

## Продолжительность выполнения

30 минут (0 ч. 30 мин.)

## Максимальный балл

25 баллов

## Текст задания

Разработать функционал генерации отчётов с визуализацией данных из PostgreSQL через API и GUI-интерфейс.

## Требования к базе данных

Создать таблицу sales в базе данных PostgreSQL со следующей структурой:

| **Имя поля** | **Тип данных** | **Описание** |
| --- | --- | --- |
| id | SERIAL PRIMARY KEY | Идентификатор |
| product_name | VARCHAR(100) NOT NULL | Наименование товара |
| category | VARCHAR(50) NOT NULL | Категория |
| quantity | INTEGER NOT NULL | Количество |
| price | DECIMAL(10,2) NOT NULL | Цена за единицу |

Заполнить таблицу не менее чем 10 тестовыми записями.

## Требования к API

- GET /api/reports/sales-summary — сводный отчёт по продажам
- Возвращает агрегированные данные: {"summary": [{"group": "…", "total_quantity": N, "total_revenue": N},…]}
- Группировка по категории (SUM по quantity, SUM по quantity × price)
- HTTP 500 при ошибке сервера

## Требования к GUI интерфейсу

- Кнопка «Построить отчёт»
- Столбчатая диаграмма (QBarSet + QBarSeries из QtCharts) по категориям
- QTableView для отображения табличного отчёта
- Заголовок диаграммы «Продажи по категориям»
- При пустом результате отчёта — сообщение «Нет данных»
- При ошибке сервера — информативное сообщение об ошибке в GUI

## Требования к тестированию

Составить пакет тест-кейсов (не менее 6 тест-кейсов) для проверки API отчётов и GUI.

Каждый тест-кейс должен содержать:

- ID тест-кейса
- Название
- Предусловия
- Шаги тестирования (пошагово)
- Ожидаемый результат
- Фактический результат (оставить пустым для заполнения экспертом)
- Приоритет (high / medium / low)

Обязательные тест-кейсы:

1. Получение сводного отчёта без записей (пустой массив)
2. Получение сводного отчёта с данными (проверка суммы и количества)
3. Проверка корректности расчёта total_revenue (quantity × price)
4. Построение диаграммы в GUI по данным отчёта
5. Отображение пустого отчёта в GUI (сообщение «Нет данных»)
6. Ошибка сервера при недоступной БД (HTTP 500)
